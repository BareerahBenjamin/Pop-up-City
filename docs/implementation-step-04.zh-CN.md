# 第四步：签到在线通知与消费确认

日期：2026-10-19。状态：后端本地实现及测试完成；未部署、未修改正式数据库、未构建或烧录固件。

## 已实现

新增0015_device_notifications.sql，持久化在线会话、不可复用会话编号和签到通知。单人发起者签到及新持久化批量签到的共享保存服务中，只有首次插入签到才创建通知；签到、结算任务、回执及通知一起提交或一起回滚。已有签到和重复请求不会重复创建提醒。

只有签到产生时持有有效在线会话的对应成员板才有提醒。没有在线会话的成员仍保存正常签到结果，联网后通过runtime/records同步，不补建提醒。通知只含本人成员板对应的操作编号、活动编号、时间和亮起指令，不返回名单、邮箱或令牌。

短时会话租约10秒，建议每2秒轮询续期；通知有效期不超过产生后10秒、创建时会话到期时间和活动结束时间。取消或结束活动后不再下发排队提醒。网络连接是否在线只能通过租约近似判断；即时物理断线由固件检测并换会话，后端不能独自保证断线那一刻感知。

## 接口

沿用设备Bearer认证，事务内再次检查有效绑定、成员未停用、成员板类型。成功响应为{payload,signature}，包含recipient_device_id，Cache-Control:no-store；固件必须先验证签名和接收设备。错误返回现有错误格式。

### POST /api/device/feedback/session

请求：`{"session_id":"新的小写UUID"}`。

开机或每次网络重连生成新编号。响应session_id、expires_at、poll_after_ms。建立新会话不读取旧队列；旧会话编号永久不可复用。当前会话请求响应丢失可用相同编号重发，但不会延长租约，过期返回SESSION_EXPIRED；已被替换的编号返回SESSION_REUSED。

### GET /api/device/feedback?session_id=UUID

仅当前未过期会话可用，成功轮询将租约延长10秒。返回server_time、expires_at、poll_after_ms和最多30条未确认且未过期通知，按notification_id递增。

items包含notification_id（持久化递增编号）、interaction_id、activity_id、created_at、expires_at、feedback:checkin_pulse、duration_ms:1000。过期或活动取消的记录不下发，旧会话记录也不下发。会话过期返回SESSION_EXPIRED，不自动恢复旧提醒。

### POST /api/device/feedback/ack

请求：`{"session_id":"当前会话UUID","notification_ids":[1,2]}`，单次最多30个正安全整数。

仅确认属于本设备与该会话的通知；重复ACK无副作用，未知/他人编号不会泄露或修改其记录。已更换会话的ACK拒绝。ACK不修改签到事实、成长或星球。

## 固件必须遵守的消费顺序（待接入）

1. 每次开机/断网恢复创建新会话；先按既定流程同步事实及核对未决写入。历史结果不亮起。正常联网时维持2秒轮询，不与5秒runtime轮询混淆。
2. 验证响应签名、recipient_device_id和当前session_id。延迟响应属于旧连接必须丢弃；按已校准服务器时间检查通知未过期，Wi-Fi已断或当前活动失效时不播放。
3. 按notification_id顺序消费，以“会话编号+最大已消费通知编号”作本地持久化消费游标。**先保存游标，再亮起1秒，再ACK**。相同/更小编号只补ACK，不再亮起。轮询和消费串行，避免两个回调同时播放。
4. 保存消费游标失败时不亮起也不ACK。先保存后掉电可能丢失一次视觉反馈，但不会重播；签到事实始终保留。这是避免重复亮起的明确取舍，后端ACK本身无法做到视觉效果恰好一次。
5. ACK超时保留原编号重发，不生成新签到请求。通知查询/ACK失败不应撤销成功签到。

目前未改固件，以上消费游标及1秒视觉逻辑不能宣称已在实机验证。旧设备协议的直接近场回执也可能触发亮起，新固件接入时必须统一走同一消费去重入口，避免近场回执和云通知各亮一次。
