# 个性化加好友动画设计

状态：2026-10-19 个性化外观整合中；15 款发型已经逐一目视审查，尚未实机验收。0.2.0-rc1 默认人物候选包已撤回。

## 已确认的显示效果

- 使用现有简洁像素小人，保留靠近、碰面、爱心动作，不把官网头像缩成大头贴。
- 每块板子的机主在左、好友在右；两人同时以相同速度向中间靠近。
- 根据官网头像提取发色、衣服颜色，发型区分短、中、长。
- 长发仅在人物后侧延伸，不画脸前侧的竖线；脸上只保留眼睛，不画像胡子的彩色横线，也不从官网素材复制胡子。
- 不恢复左上角名字、星球下方标题或录音功能。Wi-Fi 在左上角，电量在右上角。

## 数据源与发型映射

以数据库 `members.avatar_json` 中的 `release`、`selection` 为唯一外观来源，按设备当前绑定的 member_id 查找，不按昵称或导出文件中的排序查找。

网站素材版本 `herstory-avatar-assets-v1` 的15款发型已经逐一查看，静态映射记录于 `hardware-cloud/avatar-style-map.json`，包含来源摘要、发长和主色。判断采用后侧轮廓：不到下巴为短发，下巴至肩部为中发，超过肩部为长发；胡须不计入发长，不按资产编号猜测。

建议建立 `hardware-cloud/avatar-style-map.json`，键包含素材版本和资产 ID，每项保存发长枚举及显式确认的颜色。发色可用素材主色提取辅助建立映射；不能让眼睛、黑色描边、装饰线或背景色覆盖发色。

衣服优先取实际显示的叠穿 `hst_layer_hoodie`；叠穿为 none 时取 `hst_layer_body`。衣服颜色选择主体面料颜色，忽略肤色和轮廓。基础肤色、鞋子及动作风格统一，首版不扩展到表情、耳饰、卷曲程度或其他服装款式。

导出的全员 JSON 仅用于预览和覆盖检查，不作为运行时数据源。网站成员后续完成头像后，下次交友自动读取数据库，无需重新导出或烧录。

## 服务端与接口

复用 `hardware-cloud.js` 与 `hardware-cloud/friend-session.mjs` 的现有 `/local/friend/*` 接口，在已匹配的 waiting/done 会话响应中追加可选 `visual` 字段。外观来自当前会话双方设备绑定的成员，不接受客户端指定任意成员 ID。

```json
{
  "visual": {
    "version": 1,
    "template": "pixel-friend-v1",
    "self": {
      "member_id": "<当前设备绑定成员UUID>",
      "hair_length": "long",
      "hair_rgb": "A787F6",
      "shirt_rgb": "FFFFFF",
      "fallback": false
    },
    "peer": {
      "member_id": "<本次会话对方成员UUID>",
      "hair_length": "short",
      "hair_rgb": "A9482B",
      "shirt_rgb": "FFFFFF",
      "fallback": false
    }
  }
}
```

示例颜色取自既有试样；其中 long/short 只演示协议，不代表已完成这两款素材的发长审定。版本1固定 RGB 六位十六进制和 short/medium/long 枚举，板子校验版本、长度和范围。

`self`/`peer` 由服务端面向响应接收者排列。同一对成员在两块板子上自然交换左右，不能使用按 UUID 排序的 device_a/device_b 直接决定左右。

参数放入现有签名 payload 中，复用接收设备的响应签名与 recipient_device_id 校验；不增加数据库直接连接、不返回邮箱或头像原图、不改动现有双边确认及好友提交的规范化签名文本。

会话首次成功生成参数时固定双方外观快照，重试及两台设备读取使用同一份；只在 waiting/done 会话暴露。短生命周期的会话状态可沿用当前持久化方式保存这些非凭据参数，不新增正式业务表或数据库迁移。需要分别按设备调整 self/peer，不能直接保存第一个请求者的左右排列并发给另一个人。

映射失败和头像 JSON 损坏仅导致 visual 默认化。外观读取或转换失败不得被当成好友提交失败，且不得重复执行已成功的好友提交。

## 硬件渲染

使用与已确认试样一致的小人几何模板，短、中、长发三种后侧轮廓；颜色由参数控制。动作按经过时间计算，而不是累积位移，避免循环稍慢造成左右速度不同。

- 原生画布112×80，以最近邻2倍显示为224×160，位于240×320屏幕的 (8,60)。
- 16帧，每帧150毫秒，约2.4秒；最终显示爱心与好友成功提示。
- 实现使用原生 RGB565 strip 叠加，复用面板现有 240×10 DMA 缓冲；不新增整帧缓冲、不使用 LVGL I4 缓存。
- 每行直接按经过时间计算人物位置与外观，绘制中不分配堆、不发网络请求、不写 Flash。
- 动画与最终停留页复用同一份已验证外观；不把最终画面替换回旧的固定短发图片。
- 不释放星球数据或个人存档；真实双板、连续交友及最小堆情况仍需实机验收。

## 触发与交互

1. 搜索和靠近：沿用现有双向近距校验。
2. 匹配到对方：在原会话响应中顺带接收外观；这一阶段不播放成功动画。
3. 双方确认、服务器保存好友关系、板子验证成功回执后，才开始动画。
4. 同一 interaction_id 重复轮询或重试不会重复播放。重复添加已有好友显示“ALREADY FRIENDS”，可复用短动画，但不能重复创建关系。
5. 播放期间按键锁定；播完停留，再短按 OK 经 loading... 返回星球（若本人活动正在进行则进入签到）。长按 OK 开关可用页面的说明，电源键只控制硬件电源。短按 UP 换网仅在星球页生效。动画不得阻塞主循环。
6. 动画结束后显示成功及“OK return to planet”；按 OK 回到星球。断网、重启或退出画面不会删除已保存好友。

复用匹配响应携带参数，不在播放前增加独立头像请求。两台设备可以因收到成功响应的时间不同而先后开始；首版不承诺跨设备严格同步，只保证每台屏幕中的两人同步靠近。

## 兼容与默认形象

- 没有头像、未知素材 ID、未知 release、损坏参数：对应人物使用统一默认短发和配色；有头像的一方仍使用真实外观。
- 已保存好友但没有完整 visual：显示成功和外观同步提示，按 OK 可返回；仅只读查询原回执，不重新提交好友。明确 fallback=true 的无头像人物可以使用默认外观。
- 旧板子忽略新增可选字段；新板子连接缺 visual 的旧服务器时不会假装读取到了头像，需部署配套网站版本。
- 不新增个人分区、保存点或持久头像缓存。当前42个有头像成员、35个无头像成员均可交友；第一周名单27个有头像、17个无头像用于覆盖测试，不能把无头像当成错误账号。

## 验证与发布

服务端测试：15款发型映射全覆盖、无多余映射、基础服装/叠穿优先级、损坏头像、双方左右互换、签名包含外观、无关设备不可查询、重复确认不重复保存，外观失败不影响好友成功。

硬件主机测试：三种发长、颜色范围、未知版本默认化、帧边界、计时回绕、同一回执不重播、任意帧绘制边界、I4 编解码与 PNG 预览一致。构建后确认旧录音和姓名显示未被带回。

真机测试：两块分别绑定不同成员，互相作为机主验证左右；短/中/长发组合与双方同时靠近；正常加好友、重复添加、丢网、缺头像、OK 跳过、长按 UP、回星球；记录动画前后最小剩余堆和最大连续块，观察重复交友20轮是否崩溃或累积泄漏。只能在完成实测后报告这些项目通过。

实施顺序：确认15款发型映射与三档外观预览，完成服务端及主机测试，再实现硬件通用渲染并构建，最后按用户授权部署和烧录双板验证。仅本地文件修改；push、PR、merge 均由用户操作。
